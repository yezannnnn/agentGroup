实战案例：Aegis 审批按钮无响应修复

SDD + TDD + Harness范式完整流程演示

问题输入

🐛 Bug报告: "Aegis审批弹窗，点击批准/拒绝按钮没反应"
🎯 期望: 点击后执行对应操作并关闭弹窗

范式流程应用

🔍 阶段1: 问题分析 (概念层)

SDD视角: 哪个skill出了问题？
→ 识别为 approval-handling skill故障

Harness视角: 哪个组件失效？
→ 前端事件处理器 or 后端API调用链

输出: diagnosis-aegis-approval-bug.md

🏗️ 阶段2: 架构诊断 (设计层)

Harness分析: 组件间通信失败
→ ApprovalModal.vue → Backend API → Database
→ 哪一环断了？

SDD分析: 相关技能梳理
→ frontend-interaction, api-integration, database-operation

输出: architecture-trace-aegis.md

🧪 阶段3: TDD修复 (开发层)

1. 先写失败测试
test-approval-click-response.js
```js
it('should respond to approval click', () => {
  clickApprove(); // 当前会失败
  expect(modal).toBeHidden();
});
```

2. 定位具体故障点
→ 发现: API调用成功，但前端没有处理response

3. 最小修复
→ 修复事件处理器回调

输出: 修复代码 + 通过的测试

🚀 阶段4: Runtime集成 (Runtime层)

Harness更新: 修复集成到runtime
→ 更新 approval-handling skill版本
→ 验证Harness兼容性

SDD验证: Skill功能完整性
→ 确保相关skills协同正常

输出: 部署包 + 集成测试报告

🎯 交付物清单

文档输出

  • diagnosis-aegis-approval-bug.md
  • architecture-trace-aegis.md
  • fix-approval-click-prd.md
  • test-results-report.md

代码输出

  • 修复的组件代码
  • 新增测试用例
  • 更新的skill定义
  • Harness配置更新
✅

优点分析

  • 可追溯性: 每个阶段有明确文档
  • 标准化: 不同人修bug流程一致
  • 质量保证: TDD确保不引入新bug
  • 技能积累: Bug修复变成技能资产
  • 架构改进: Harness不断完善
⚠️

缺点分析

  • 过度工程: 简单bug走复杂流程
  • 时间成本: 比直接改代码慢
  • 学习曲线: 团队需要适应范式
  • 工具依赖: 依赖Harness和skill体系
  • 灵活性降低: 紧急修复可能被流程拖累

💡 关键洞察

这套范式适合 重复性、可积累的开发工作，让每次bug修复都变成团队资产。但需要在 标准化收益 vs 敏捷性 之间找平衡点。
