# agent-group v5 完整执行总计划

## 1. 文档目的

本计划基于 `D:\git_desun\sc-cloud\agent-group\claude-demo\agent_group_simp_v5.md` 重构为可执行版本，目标不是重复方案原文，而是把 v5 落成一组可以直接推进、检查、回退的执行计划。

本计划遵循以下原则：

1. 实事求是，只以原文中已经明确的结构和约束为基础，不虚构额外机制。
2. 先稳定协作闭环，再做物理迁移和体验优化。
3. 正式任务系统、协商系统、状态系统必须边界清晰。
4. 每一步都必须具备进入条件、输出物、验收标准、失败回退方式。

## 2. 总目标

在不打断现有协作的前提下，把 `agent-group` 收敛为一套稳定协作体系：

1. 角色结构收敛为 `max / ella / jarvis-fe / jarvis-be / kyle`
2. 正式事实源收敛为 `proposal.md / design.md / tasks.md / _meta.yaml`
3. Cross-Tag 从“临时协商”收敛为“可被 Max 固化的闭环输入”
4. 审查入口收敛到同一 `change`
5. 历史与活跃数据具备清晰治理边界

## 3. 执行总策略

### 3.1 总体顺序

按以下顺序推进，不建议并行跳步：

1. 先做基础准备与事实源治理
2. 再做角色拆分与兼容入口治理
3. 再做 `_meta.yaml` 状态层上线
4. 再做 Cross-Tag 固化闭环
5. 再做统一提审与联合审查
6. 最后做归档与启动性能治理

### 3.2 为什么这样排

原因很直接：

1. 如果正式事实源未统一，后续所有角色拆分都会继续依赖口头约定。
2. 如果角色未拆分，Cross-Tag 没有真实使用场景。
3. 如果 `_meta.yaml` 未上线，Cross-Tag 与评审状态无法统一聚合。
4. 如果评审入口未统一，FE/BE 联动需求仍会碎裂。

## 7. 统一执行口径

所有子计划必须统一遵守以下口径：

1. 正式任务只认 `tasks.md`
2. 正式验收只认 `tasks.md`
3. `_meta.yaml` 只承载状态，不承载正文设计
4. Cross-Tag 只作为协商输入，不直接成为正式任务源
5. 代码最终只由 `jarvis-fe` 和 `jarvis-be` 产出
6. 任何新增流程都必须保留回退路径

## 8. 推荐试点方式

不要直接全量迁移，建议采用一个中等复杂度、同时涉及 FE/BE 的需求做试点。试点标准如下：

1. 有明确页面改动
2. 有明确接口或数据结构改动
3. 能触发至少一次 Cross-Tag
4. 能触发一次统一提审
5. 不涉及过多外部系统

## 9. 总体验收标准

当以下条件同时成立时，视为 v5 执行计划达成：

1. 新需求默认走 `jarvis-fe / jarvis-be` 双角色协作
2. 新 change 默认具备 `proposal.md / design.md / tasks.md / _meta.yaml`
3. Cross-Tag 能在 1 个工作周期内形成“提出 -> 固化 -> 执行 -> 提审”的闭环
4. Kyle 能从同一 `change` 完成审查
5. 归档机制上线后，活跃目录保持可控

## 10. 总体回退原则

如果任一阶段引发明显混乱，回退时遵守以下规则：

1. 优先回退流程使用方式，不回删目录结构
2. 保留已创建的模板与文档，避免二次建设
3. 先恢复到上一层稳定入口，再定位问题
4. 不在同一轮中同时回退多个阶段

## 11. 执行组织方式

为避免“有方案、无推进人”，建议在执行期临时固定 5 类责任人：

1. 方案 owner
   - 对总节奏负责
   - 决定阶段是否进入下一步
2. Max 规则 owner
   - 负责正式事实源、`_meta.yaml`、sync 固化规则
3. FE 迁移 owner
   - 负责 `jarvis-fe` 入口与试点执行
4. BE 迁移 owner
   - 负责 `jarvis-be` 入口与试点执行
5. 审查 owner
   - 负责 Kyle 审查模板与闭环

若当前没有固定人选，也至少要指定“谁拍板、谁执行、谁验收”三类角色，否则计划容易停在文档层。

## 12. 统一阶段门禁

每个子计划都必须经过 4 类检查，才允许进入下一阶段：

1. 结构检查
   - 目录、模板、说明文件是否齐备
2. 规则检查
   - 责任边界是否写清楚
3. 试运行检查
   - 是否至少跑过一次真实或半真实场景
4. 回退检查
   - 出问题时是否知道怎么退回上一稳定状态

不满足这 4 项中的任意一项，都不建议宣告“阶段完成”。

## 14. 试点 change 选择标准

为了避免试点过轻或过重，建议按以下标准选择：

### 必须满足

1. 同时涉及 1 个页面改动和 1 个接口改动
2. 能明确拆出至少 2 条正式任务
3. 预计能在 3 到 5 个工作日内完成

### 不建议选择

1. 纯文档需求
2. 纯 UI 微调需求
3. 涉及大规模数据库迁移的需求
4. 依赖外部团队排期的需求

### 推荐特征

1. 页面导出
2. 列表筛选增强
3. 表单提交流程补字段
4. 小范围数据结构调整

## 15. 执行时的统一检查表

每推进一个 change，可按以下顺序检查：

1. 是否已创建 `proposal.md`
2. 是否需要 `design.md`
3. `tasks.md` 是否已经明确 FE 与 BE 正式任务
4. `_meta.yaml` 是否已创建且字段完整
5. FE/BE 是否按各自入口启动
6. 是否出现边界缺口
7. 若出现边界缺口，是否发起 Cross-Tag
8. 若需正式纳管，是否同步生成 sync request
9. Max 是否已处理 `pending_syncs`
10. 开发完成后是否生成提审单
11. Kyle 是否按同一 change 审查
12. 通过后是否满足归档条件

## 18. 失败信号清单

出现以下信号时，说明改造方向正在跑偏，需要暂停推进：

1. `tasks.md` 之外开始长期维护任务清单
2. `_meta.yaml` 被写成长篇说明
3. `jarvis/` 仍是主要执行入口
4. Cross-Tag 长期堆积无人处理
5. Kyle 主要依据 handoff 而不是 `tasks.md` 审查
6. 活跃区与归档区开始混放

这 5 项是 v5 真正不可再压缩的最小骨架。
