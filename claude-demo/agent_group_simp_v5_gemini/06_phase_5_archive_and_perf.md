# Phase 5: 历史沉淀归档与系统的检索性能治理 

## 5.1 阶段目标
针对随着时间推进产生的大批不再被需要的讨论记录或者“完成案卷”造成系统的严重臃肿减慢。
通过合理的“死卷”归档流程降低 LLM 启动或者加载分析背景上下文时候的无效 Token 浪费提升推理执行速度，同时兼顾所有过往工作记录的历史可回滚与可追溯性。

## 5.2 核心操作流程与职责

### 归档对象 1：中心任务仓库 (Openspec Changes)
针对需求层级。
- **触发人与条件**：当某一 Change 所有代码任务完全被签入（Kyle 通关）且上线后，由 Max 判断并启动。
- **操作实质**：
  1. 将整个存放在 `openspec/changes/<change-name>/` 下所有相关正式任务、需求底稿统统搬迁打包移动到闲散库区 `openspec/archive/<change-name>/` 下。
  2. 收尾修改旧有的 `_meta.yaml`。将生命周期状态改为 `archived`。并将 `archive.archived` 改为 `true` 并补全 `archived_at`（操作时间戳） 和可选的 `archive_reason`。

### 归档对象 2：交接与协同区沉淀 (Handoff Artifacts)
针对过程交互池（各类讨论冗长甚至极细碎的小修补）。
- **触发条件**：一旦原属的 Change 已经宣布完结甚至归档或者该 Cross-Tag (sync-xx) 已被正式融入任务或被永久性放弃驳回且时日较长。
- **操作实质**：Max (或者对应的操作者) 将该相关条目及所有 Inbox 审阅回复移送至冷存位置 `shared/handoff/archive/` 里分类挂放。

## 5.3 搜索性能收口机制优化
因为对 `openspec/changes` 的精简处理，后续的常态扫描检索算法（预加载）须设定在仅仅过滤或寻址未被移交 archive 并且未在 `.yaml` 里挂载废弃属性的内容。
1. **活跃控制管理**：启动初期加载只强制看取 `in-progress` 及 `ready` 附近活跃属性事件树，规避全面大盘加载引发卡顿及超时。
2. **`status.json` 精简直连**：虽然被降级为数据概览版，但在渲染它时也同样利用归档标识别去除掉已被封存的历史清单让 JSON 的常驻状态瘦身。

## 5.4 阶段考核达成面检验规则
1. 当前系统里作为主业务库的所有内容始终保持少而精（不含历史遗留包袱问题累积出来的几十上百个项目）。
2. 在任意时刻提供 `change-id`，都能稳健在 archive 区挖掘连带的出处来源及审批细节反馈历史，保证法务及工程规范审计不受碍。
3. 任何一次前端启动智能体的扫盘时长应缩在极小常数级规模。

## 5.5 回退建议
如果发生因为操作逻辑有漏洞导致活跃库的文档莫名被移走从而开发卡断的：
- 禁止立刻再次运用自动归档插件或脚本转移命令。
- 取档恢复所有相关状态到原 `changes/` 库下修复参数后再行执行归档，因为所有历史都不会遭受实体毁灭。
