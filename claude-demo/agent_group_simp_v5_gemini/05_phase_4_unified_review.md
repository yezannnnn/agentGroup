# Phase 4: 基于统一 Change 的审查防线规约 (KYLE 收口) 

## 4.1 阶段目标
结束过往按前后端单独“割裂审查”和不同时步审查造成的信息孤岛效应。促使 Kyle（QA 测试员/复检架构员）**以宏观相同的一个 change 为基准作为大单位做统合逻辑验收**。使得关联变动的 FE 与 BE 代码得到充分验证。

## 4.2 统一输入模型搭建

**多重上下文拼合抓取：**
让 Kyle 能看得全一个请求来龙去脉的最核心方式就是赋予他同时追源的义务。Kyle 开启对某一条目的核实工作时：
- 强制**必须读取**项：宏观定义验收边界的 `tasks.md` + 提交者放在 `shared/handoff/jarvis-to-kyle/<change>.md` 下的该提审单主卷。
- **关联选读**项：如果其代码涉及 UI 可去回访 `design.md`；如里面提及解决过某矛盾可去回溯 `Cross-Tag` 记录；并且审查开发自留的自查报告（存在于 `shared/superpowers/reviews/`）。

**提审请求单结构约束表:**
生成于 `jarvis-to-kyle/` 供 Kyle 获取的单子应当形如下面要求：
```markdown
# 审查请求: <change-name的通读名>
- 提交者: jarvis-fe / jarvis-be   （注：如为联合提交写清楚贡献成分）
- 关联 change: <change-name>
- 自查报告: <对应 shared/superpowers/reviews/该次工作的记录目录>

## 变更范围
<本笔提交修改了什么大类逻辑以及那些相关组件，精明扼要>

## 关联任务
<回溯对标在 tasks.md 里它算解决或者部分解决了里面编排的哪几条正式 task>

## 验收基准引述
<将其在 tasks.md 里设定的合格红线照搬回此处用作 Kyle 审核对标>
```

## 4.3 联合交叉审查与反馈输出路径
**反馈输出:**
一切查阅核对或者对代码做静态扫描之后的漏洞、反馈问题必须系统性落进 `shared/handoff/kyle-to-jarvis/<change>.md` 里回下级执行打磨。
该返回单**至少涵盖四部分结构**：
1. **审查范围**：本次看了哪些文件以及针对那些 tasks 做了结论审查。
2. **问题清单**：按照条理顺出来的缺陷列表（如果直接报错也要贴回错误或者复原推演）。
3. **严重阻击度分类**：区分列出（Blocking - 阻塞需立即重启 / Non-blocking - 仅记录瑕疵等有空优化）。
4. **建议的回归检查法**：为二次修改通过者提供回归标准。

**并行关联提交应对法:**
前端与后端如果是响应同一大需求的同步作业：
1. 仍然可以在自己的沙箱内异步平行产出。 
2. 但一旦涉及彼此高度交联时，提审材料尽量归拢对齐指向同一 `change-name` 档案节点。
3. Kyle 读到同一 change 号，即可进行全景式复盘保证两侧逻辑拼接完全严密扣紧。

## 4.4 风险对策与回退 (Rollback)
最大的风险在于要求前端等待后端的逻辑会导致一方代码被扣留在送审流水线上过久（反之亦然）。
一旦出现审核等待时长不可控和多重冲突缠绕：
- 暂时保留各自独立发起独立 change 序列提审通过的能力作为降配兜底。
- 让 Kyle 返回到最基础的一单一验，由其手工输出口头核查反馈由人类在终端进行统筹汇总。
