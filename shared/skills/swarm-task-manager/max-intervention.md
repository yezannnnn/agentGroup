# Max 介入决策指南

本文档定义 Max 何时需要介入，以及介入后的处理流程。

---

## 🚨 介入触发条件

### 自动触发（硬性限制）

当以下情况发生时，系统**必须**停止当前 spawn 链，通知 Max 介入：

#### 1. 层级超限 (LAYER_OVERRUN)
```
触发条件: 继续 spawn 将导致层级超过 Layer 3

示例:
- Max (Layer 1) → Jarvis (Layer 2) → Kyle (Layer 3) → 尝试 spawn 其他人 ❌
- 这是禁止的，Kyle 是终点角色

处理:
1. 拒绝 spawn
2. 立即通知 Max
3. Max 评估是否需要人工协调
```

#### 2. 权限违规 (PERMISSION_DENIED)
```
触发条件: 角色尝试 spawn 不允许的目标

示例:
- Kyle 尝试 spawn Jarvis (Bug修复)
- Ella 尝试 spawn Kyle

处理:
1. 拒绝 spawn
2. 告知正确的流程（应该通知 Max）
3. Max 收到通知后协调
```

#### 3. Bug循环超限 (BUG_LOOP_EXCEEDED)
```
触发条件: 同一 Bug 修复超过 3 轮

第1轮: 发现 → 修复 → 验证 ❌
第2轮: 详细说明 → 修复 → 验证 ❌
第3轮: 最终尝试 → 修复 → 验证 ❌
第4轮: 🚨 强制停止，Max介入

处理:
1. 停止所有相关 spawn
2. Max 分析根因
3. 汇报用户，等待决策
```

#### 4. 成本告警 (COST_ALERT)
```
触发条件: 单任务累计 Token 超过阈值

阈值:
- 警告: 5,000 tokens
- 严重: 10,000 tokens
- 强制停止: 20,000 tokens

处理:
- 警告: Max 关注，评估是否需要优化
- 严重: Max 介入分析
- 强制停止: 必须汇报用户，讨论是否继续
```

#### 5. 上下文丢失 (CONTEXT_LOST)
```
触发条件: 无法确定原始需求或目标

症状:
- 子代理反复询问已回答过的问题
- 执行方向与原始需求偏离
- 多个子代理对任务理解不一致

处理:
1. 停止当前执行
2. Max 重新梳理需求
3. 必要时与用户重新确认
```

### 人工触发（软性判断）

以下情况建议 Max 介入，但非强制：

#### 6. 需求变更 (REQUIREMENT_CHANGE)
```
症状:
- 用户提出新的需求
- 原有需求发生变化
- 范围不断扩大（范围蔓延）

决策:
- 小变更: Max 直接调整
- 大变更: 汇报用户，重新规划
```

#### 7. 方向分歧 (DIRECTION_DISPUTE)
```
症状:
- Ella 和 Jarvis 对设计方案有分歧
- Kyle 认为实现不符合预期，但 Jarvis 认为符合
- 多个解决方案，难以决策

决策:
- Max 评估各方案优缺点
- 必要时引入用户决策
```

#### 8. 外部依赖 (EXTERNAL_DEPENDENCY)
```
症状:
- 需要外部 API/服务
- 需要用户提供的资料/账号
- 需要第三方审核/确认

决策:
- 记录依赖项
- 通知用户
- 暂停任务，等待外部条件
```

#### 9. 质量异常 (QUALITY_ANOMALY)
```
症状:
- Bug 率异常高（每个功能点 >3 个 Bug）
- 修复引入新问题（回归 Bug）
- 代码审查发现系统性问题

决策:
- 分析根因（需求不清？设计缺陷？实现问题？）
- 决定是继续修复还是重新设计
```

#### 10. 用户明确要求 (USER_REQUEST)
```
症状:
- 用户说"让 Max 看看"
- 用户要求解释当前状态
- 用户对进度/质量有疑问

处理:
- Max 立即介入
- 提供透明清晰的汇报
```

## 🔄 介入后处理流程

### 步骤1: 停止与保护

```
1. 停止当前 spawn 链
   - 不要强制终止已运行的子代理
   - 但不再发起新的 spawn

2. 保存当前状态
   - 确保所有进度已记录
   - 更新 Task 状态文件

3. 通知相关方
   - 告知子代理"Max 已介入，暂停当前任务"
```

### 步骤2: 信息收集

```
1. 阅读 Task 状态文件
   - shared/tasks/current/{task-id}.md

2. 查看执行历史
   - 各轮次执行情况
   - Token 消耗统计
   - Bug 修复循环记录

3. 理解上下文
   - 原始需求
   - 已经完成的交付物
   - 当前阻塞点

4. 检查共享区
   - shared/status.json
   - shared/bugs/
   - shared/docs/
```

### 步骤3: 根因分析

使用 5 Whys 方法：

```
问题: Bug 修复超过3轮仍未解决

为什么1: 为什么 Bug 修复不了？
→ 因为修复后测试仍不通过

为什么2: 为什么修复后仍不通过？
→ 因为修复的是表面问题，根因未解决

为什么3: 为什么没有解决根因？
→ 因为根因是设计缺陷，不是代码问题

为什么4: 为什么设计缺陷没在设计阶段发现？
→ 因为技术可行性评估不充分

为什么5: 为什么评估不充分？
→ 因为时间紧迫，跳过了评估环节

根因: 流程执行不到位，技术评估被跳过
解决方案: 重新进行技术评估，必要时调整设计
```

### 步骤4: 决策树

```
根因类型?
├─ 需求问题
│  ├─ 需求不明确 → 与用户澄清
│  ├─ 需求变更 → 评估影响，重新规划
│  └─ 需求冲突 → 用户决策优先级
│
├─ 设计问题
│  ├─ 设计缺陷 → spawn Ella 重新设计
│  ├─ 设计与技术不匹配 → Ella + Jarvis 联合评审
│  └─ 设计过于复杂 → 简化设计，MVP优先
│
├─ 实现问题
│  ├─ 技术方案错误 → 重新技术评估
│  ├─ 代码质量问题 → 代码审查 + 重构
│  └─ 开发人员理解偏差 → 重新沟通需求
│
├─ 测试问题
│  ├─ 测试用例错误 → 修正测试用例
│  ├─ 测试环境问题 → 修复环境
│  └─ 测试与需求理解不一致 → 三方对齐
│
└─ 流程问题
   ├─ 跳过了必要环节 → 补充执行
   ├─ 沟通不畅 → 改进沟通机制
   └─ 范围蔓延 → 重新划定范围
```

### 定期分析

每月分析介入数据：

| 指标 | 说明 | 健康范围 |
|------|------|----------|
| 介入率 | 介入次数/总任务数 | <10% |

## 🎓 介入最佳实践

### Do's ✅
- **及时介入**: 不要等到问题恶化
- **信息完整**: 介入前收集足够信息
- **透明沟通**: 清晰汇报给用户
- **给出选项**: 不要只抛问题，要给解决方案
- **记录复盘**: 每次介入都是学习机会

### Don'ts ❌
- **不要过度介入**: 小问题让子 Agent 自己解决
- **不要偏袒**: 客观分析，不要偏向某个 Agent
- **不要拖延**: 介入后迅速决策
- **不要重复**: 相同问题多次介入，要改进流程
