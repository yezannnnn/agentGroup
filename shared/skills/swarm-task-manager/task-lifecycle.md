# 任务生命周期管理

本文档定义 aiGroup 中任务的完整生命周期，从创建到完成（或中止）。

---

## 生命周期阶段

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  创建   │ → │  分配   │ → │  执行   │ → │  验收   │ → │  完成   │
│ CREATED │    │ ASSIGNED│    │ RUNNING │    │REVIEWING│    │COMPLETED│
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
     ↑                                              ↓
     └──────────────  循环（如需要）  ←─────────────┘
     
     ┌─────────┐
     │  中止   │ ← 异常情况（Max介入/用户取消/无法完成）
     │ BLOCKED │
     └─────────┘
```

---

## 阶段1: 创建 (CREATED)

### 触发条件
- 用户提出新需求
- 现有任务衍生的子任务
- Bug修复任务

### 执行者
- Max（主任务）
- 任何 Agent（子任务，需通知 Max）

### 必须输出
```markdown
# Task: {task-id}

## 基本信息
- **任务名称**: 
- **任务类型**: feature / bug / design / review
- **发起者**: 
- **创建时间**: 
- **父任务**: (可选)

## 需求描述
### 目标
### 验收标准
### 约束条件

## 初始评估
- **预估复杂度**: 低/中/高
- **预估Token**: 
- **建议分解**: 是/否
- **建议执行者**: Ella/Jarvis/Kyle

## 状态
- **当前状态**: CREATED
- **当前层级**: Layer 1
- **当前负责人**: Max
```

### 状态流转
- `CREATED` → `ASSIGNED`: Max 决定执行者并 spawn
- `CREATED` → `BLOCKED`: 需求不明确，需要用户澄清

---

## 阶段2: 分配 (ASSIGNED)

### 触发条件
- Max 完成需求分析
- 决定需要 spawn 子 Agent

### 执行者
- Max

### Spawn 决策树
```
任务类型?
├─ 设计相关
│  └─ 需要UI/UX? → spawn Ella
│  └─ 需要设计评估? → spawn Ella → Ella spawn Jarvis (技术评估)
│
├─ 开发相关
│  └─ 需要架构设计? → spawn Jarvis (Layer 2 分析)
│  └─ 需要编码实现? → spawn Jarvis
│  └─ 需要代码审查? → spawn Jarvis → Jarvis spawn Kyle
│
├─ 测试相关
│  └─ 需要测试验收? → spawn Kyle
│  └─ 发现 Bug? → 进入 Bug修复循环
│
└─ 混合类型
   └─ 并行 spawn 多个 Agent
      ├─ spawn Ella (设计)
      └─ spawn Jarvis (技术评估)
```

### 必须输出
- 更新 Task 状态文件
- 更新 `shared/status.json` 通知相关方
- Spawn 子 Agent（使用 Task 工具）

### Spawn 内容规范
```yaml
spawn_context:
  task_id: "task-001"
  parent_task: "task-parent"  # 可选
  layer: 2  # 子 Agent 所在层级
  
  objective: "明确的任务目标"
  background: "必要的背景信息"
  
  deliverables:
    - "交付物1"
    - "交付物2"
  
  constraints:
    - "约束条件1"
    - "约束条件2"
  
  success_criteria:
    - "验收标准1"
    - "验收标准2"
  
  exit_conditions:
    - "完成标准"
    - "中止条件（如遇到X情况，停止并通知Max）"
  
  shared_context: "../shared/tasks/current/task-001.md"
```

### 状态流转
- `ASSIGNED` → `RUNNING`: 子 Agent 开始执行
- `ASSIGNED` → `BLOCKED`: 子 Agent 拒绝或无法执行

---

## 阶段3: 执行 (RUNNING)

### 触发条件
- 子 Agent 接受任务并开始工作

### 执行者
- Ella / Jarvis / Kyle

### 执行规范

#### 3.1 进度更新
每 5-10 分钟或关键里程碑：
```markdown
## 进度更新 - {timestamp}

### 已完成
- [x] 子任务1
- [x] 子任务2

### 进行中
- [ ] 子任务3 (50%)

### 遇到问题
- 问题描述 → 解决方案/需要的帮助

### Token消耗
- 当前任务: X tokens
- 累计: Y tokens
```

#### 3.2 子 Agent 的 Spawn 权限
```
Ella (Layer 2):
└─ 可以 spawn: Jarvis (Layer 3, 终点)
   └─ 场景: 技术可行性评估
   └─ Jarvis 评估完成后返回 Ella，不再继续 spawn

Jarvis (Layer 2):
└─ 可以 spawn: Kyle (Layer 3, 终点)
   └─ 场景: 代码审查/测试
   └─ Kyle 审查完成后返回 Jarvis 或通知 Max

Kyle (Layer 2):
└─ 禁止 spawn 任何人
   └─ 发现 Bug → 记录并通知 Max
```

#### 3.3 完成标准
- 交付物已完成
- 已通过自测（如适用）
- 更新了 Task 状态文件
- 准备了交接说明

### 状态流转
- `RUNNING` → `REVIEWING`: 执行完成，进入验收
- `RUNNING` → `BLOCKED`: 遇到阻塞问题

---

## 阶段4: 验收 (REVIEWING)

### 触发条件
- 子 Agent 报告任务完成
- 需要验证/审查

### 执行者
- Max（功能验收）
- Kyle（测试验收）
- 用户（最终验收）

### 验收流程

#### 4.1 标准验收（新功能）
```
子 Agent 完成 → 通知 Max
    ↓
Max 初步检查交付物
    ↓
├─ 需要测试 → spawn Kyle 测试
│       ↓
│   Kyle 测试
│       ↓
│   ├─ 通过 → Max 汇总，汇报用户
│   └─ Bug → 进入 Bug修复循环
│
└─ 无需测试 → Max 汇总，汇报用户
```

#### 4.2 Bug修复循环（重点）
```
Kyle 测试发现 Bug
    ↓
Kyle 记录 Bug 详情
    ↓
Kyle 更新 status.json 通知 Max
    ↓
Max 决策
    ↓
├─ 第1-2轮 → spawn Jarvis 修复 → Kyle 验证 → [循环]
│
└─ 第3轮未通过 → 🚨 Max介入
        ↓
    Max 分析根因
        ↓
    ├─ 需求问题 → 与用户确认
    ├─ 设计问题 → spawn Ella 确认
    ├─ 实现问题 → 详细指导 Jarvis
    └─ 测试误解 → 与 Kyle 澄清
        ↓
    用户决策后重新规划
```

### Bug修复轮次跟踪
```markdown
## Bug修复循环跟踪

### 第1轮
- **发现时间**: 
- **Bug描述**: 
- **修复时间**: 
- **修复内容**: 
- **验证结果**: ❌未通过 / ✅通过
- **遗留问题**: 

### 第2轮  
- **发现时间**: 
- **Bug描述**: (累积: 第1轮遗留 + 新问题)
- **修复时间**: 
- **修复内容**: 
- **验证结果**: ❌未通过 / ✅通过
- **遗留问题**: 

### 第3轮
- **发现时间**: 
- **Bug描述**: (累积: 前两轮遗留)
- **修复时间**: 
- **修复内容**: 
- **验证结果**: ❌未通过 / ✅通过

### 第4轮 - Max介入
- **介入时间**: 
- **根因分析**: 
- **决策**: 
- **用户反馈**: 
```

### 状态流转
- `REVIEWING` → `COMPLETED`: 验收通过
- `REVIEWING` → `RUNNING`: 需要修复，返回执行
- `REVIEWING` → `BLOCKED`: 遇到无法解决的问题

---

## 阶段5: 完成 (COMPLETED)

### 触发条件
- 验收通过
- 用户确认完成

### 执行者
- Max（汇总汇报）

### 必须输出
```markdown
## 任务完成报告

### 基本信息
- **任务ID**: 
- **任务名称**: 
- **完成时间**: 
- **总耗时**: 

### 执行摘要
- **最终交付物**: 
- **关键决策**: 
- **遇到的问题及解决**: 

### 团队协作
| 成员 | 贡献 | Spawn次数 | Token消耗 |
|------|------|-----------|-----------|
| Max | 协调 | X | Y |
| Ella | 设计 | X | Y |
| Jarvis | 开发 | X | Y |
| Kyle | 测试 | X | Y |

### Bug修复统计
- **发现Bug数**: 
- **修复轮次**: 
- **平均修复轮次**: 

### 经验总结
- **做得好的**: 
- **可以改进的**: 

### 归档
- **任务文件**: 移动到 shared/tasks/completed/
- **相关文档**: 链接到 shared/docs/

# shared/status.json 中标记为 completed

# 3. 清理临时文件
# 删除不再需要的临时文件
```

## 异常状态: 中止 (BLOCKED)

### 触发条件
- 超过3轮Bug修复循环
- 需求不明确且用户无响应
- 技术无法实现
- 用户取消任务
- 成本超出预算

### 执行者
- Max（决策）
- 任何 Agent（报告）

### 必须输出
```markdown
## 任务中止报告

### 中止信息
- **任务ID**: 
- **中止时间**: 
- **中止原因**: 
- **触发者**: 

### 已完成工作
- 

### 未完成工作
- 

### 经验教训
- 

### 后续建议
- 
```

### 中止后的处理
1. 保存所有已完成的工作
2. 记录中止原因
3. 归档到 shared/tasks/archived/
4. 通知所有相关方
5. 如有必要，安排复盘会议

            │             │             │
            ↓             ↓             ↓
       ┌─────────┐   [用户澄清]   [Max介入]
       │ RUNNING │        ↓        ↓
       │  (执行) │   ┌─────────┐   │
       └────┬────┘   │ ASSIGNED│←──┘
            │        └─────────┘
    ┌───────┼───────┐

    ↓       ↓       ↓

           │      │                  │

           │ ↓    ↓    ↓             │
           │[继续][中止][需求变更]    │
