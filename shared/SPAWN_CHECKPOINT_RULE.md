# 🔄 子代理被Spawn时的强制检查点规则

> 本文档补充主CLAUDE.md，确保子代理被Spawn时也能严格执行流程。

---

## 核心规则

### 触发条件扩展

原规则:
```
收到用户消息后，必须按以下检查点顺序输出
```

**扩展后规则**:
```
收到用户消息 或 被父代理Spawn时，必须按以下检查点顺序输出
```

---

## 被Spawn时的8个检查点

当子代理被Spawn时，**同样必须**执行8个强制检查点：

### 第0检查点 - 任务范围确认
```
📋 任务范围确认: [需求明确/需要澄清]
- 预估token消耗是否 >5000 tokens
- 任务是否符合MVP原则
- 父代理提供的任务描述是否明确具体
```

### 第1检查点 - 优化策略读取
```
📖 已读取token-optimization.md
- 必须使用Read工具读取文件前20行
```

### 第2检查点 - 智能通知检查
```
🔔 通知检查: [无新通知/发现X条新通知]
- 使用 ../shared/scripts/check_notifications_simple.sh [agent] 检查
```

### 第3检查点 - 任务分解判断
```
🎯 任务分解评估: [可分解/不可分解]
- 即使被Spawn，子任务也可能需要进一步分解
```

### 第4检查点 - Skill适用性检查
```
🧰 Skill检查: [发现适用skill/无适用skill]
- 检查 ./skills/ 和 ../shared/skills/ 中是否有匹配skill
```

### 第5检查点 - 执行路径选择
```
🤖 执行方式: [直接执行/Task分解]
- 子代理也可以选择进一步分解（如果允许Spawn）
```

### 第6检查点 - Git操作检测
```
⚠️ Git操作检测: [需要授权/不涉及]
```

### 第7检查点 - 记忆系统记录 (任务完成后)
```
🧠 记忆系统: [记录完成] 压缩率: XX%
- 被Spawn的任务完成后，同样必须记录记忆
- 命令: ../memory/utils.sh record [agent] ...
```

## 与父代理的区别

| 方面 | 父代理 (Max) | 子代理 (Ella/Jarvis/Kyle) |
|------|-------------|--------------------------|
| **触发来源** | 用户消息 | 父代理Spawn |
| **检查点数量** | 8个 | 8个 (相同) |
| **任务分解权限** | 可以Spawn子代理 | 根据权限矩阵决定 |
| **通知对象** | 用户 | 父代理 (通过status.json) |

---

## 实施要求

### 1. 父代理的责任
当Max Spawn子代理时，必须在Task prompt中明确：
```
你被Max Spawn执行设计任务。

重要: 你必须严格执行8个强制检查点，就像直接收到用户消息一样。
参考: ../shared/SPAWN_CHECKPOINT_RULE.md

任务描述: ...
```

### 2. 子代理的责任
被Spawn时，在CLAUDE.md开头添加显式声明：
```markdown
## 被Spawn时的检查点执行

我被Spawn时，**同样必须**执行8个强制检查点。
参考: ../shared/SPAWN_CHECKPOINT_RULE.md

执行顺序:
1. 📋 任务范围确认 (检查父代理提供的任务)
2. 📖 读取token-optimization.md
3. 🔔 通知检查
4. 🎯 任务分解评估
5. 🧰 Skill检查
6. 🤖 执行方式选择
7. ⚠️ Git操作检测
8. 🧠 记忆系统记录 (完成后)
```

---

## 物理记录要求

每次被Spawn并完成任务后，子代理必须：
1. 在自己的记忆文件中记录
2. 在父代理的Spawn统计中留下记录
3. 更新 shared/CHECKPOINT_EXECUTION_LOG.md (如果是严格执行的示例)
